# QA-портфолио Rick and Morty React

Учебный QA-кейс для опубликованного каталога персонажей и эпизодов «Рика и Морти»: функциональные проверки интерфейса, негативные сценарии, клавиатурная навигация, адаптивность и оформление дефектов.

**Результат прогона 16 ноября 2026 года:** из 15 браузерных тест-кейсов 13 Passed и 2 Failed. Зарегистрированы два воспроизведённых дефекта с предложенной severity Minor; они ожидают триажа. Отдельно запущены существующие 15 тестов Vitest — все прошли.

## Окружение и способ проверки

- Дата: **16.11.2026**, часовой пояс Europe/Moscow.
- ОС: **macOS 27.0.1**, build 26A434.
- Браузер: **встроенный браузер**. Версия браузерного движка инструментом не предоставлена; результаты не обозначаются как прогон в отдельном Google Chrome.
- Основной CSS viewport: **1440 × 1000**. Адаптивность дополнительно проверена при **320 × 1000** и **768 × 1000**.
- Исходники: `b70fef2810896b9764e5175dd239ae6b145df485`; в демке наблюдался bundle `/rick-and-morty-react/assets/index-PFm8c2b1.js`.
- Автотесты: Node.js 24.22.1, Yarn 1.22.22, Vitest 3.2.4 и jsdom.

Материалы подготовлены для учебного QA-проекта на основе инструментального браузерного прогона. Это зафиксированный инструментальный прогон, предназначенный для изучения и самостоятельного повторения; самостоятельный ручной прогон кандидата в Chrome здесь не заявлен.

## Основание для ожидаемых результатов

Проверки основаны на функциональности, описанной в основном README, наблюдаемом интерфейсе и сформулированных для этого учебного прогона критериях приёмки. Для клавиатурного поиска ожидается сохранение логической позиции фокуса, а при переходе между каталогами — доступность начала нового каталога. Эти UX-критерии предложены QA; severity и priority дефектов требуют согласования при триаже. Полный аудит WCAG не проводился.

Браузерные результаты, Vitest с моками и просмотр исходников разделены. Скриншоты подтверждают видимое состояние; переход фокуса и координаты подтверждаются также журналом наблюдений. Просмотр кода используется для гипотез о причине дефекта, а не вместо воспроизведения.

## Границы покрытия

Выполнены браузерные сценарии каталогов, поиска, фильтров, пагинации, истории, модалки, пустого результата, клиентской страницы 404 и адаптивности. Дефекты зафиксированы в проверенной версии; production-код в рамках подготовки документации не исправлялся.

Реальные Offline/замедление сети, другие браузеры и физические мобильные устройства не проверены. Отказ запроса и повторная попытка подтверждены существующими Vitest с mocked fetch. Три прямых API-запроса из терминальной сети получили HTTP 403 с диагностическим ответом: независимая live-проверка API заблокирована этой сетью, что не классифицировано как дефект приложения. В браузере каталоги и поисковые результаты загрузились; HTTP-коды этих браузерных запросов отдельно не снимались.

Набор Playwright, Postman-коллекция и учебная SQL-база в этот пакет не входят. Их можно добавить следующим этапом с отдельными результатами запусков.

## Как повторить прогон

1. Открыть демо и зафиксировать дату, браузер с версией, ОС, viewport и проверяемую версию приложения.
2. Выполнить [кейсы TC-01—TC-15](test-cases.md), заполняя новый фактический результат для своего окружения. Исходный прогон от 16.11.2026 сохранить для истории.
3. Повторить шаги из [баг-репортов](bugs/README.md), приложить собственные скриншоты и отметить, воспроизвелись ли дефекты.
4. В локальном проекте выполнить `yarn test` и `yarn type-check`. Их результаты учитывать отдельно от браузерных кейсов.
5. Создать новый отчёт о прогоне с датой, результатами и ограничениями. После исправления дефектов выполнить ретест и обновить их статусы.
