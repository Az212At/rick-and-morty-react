# Тест-кейсы React-версии Rick and Morty

Дата выполнения: **16 ноября 2026 года, Europe/Moscow**.

Объект проверки: [опубликованная React-версия](https://az212at.github.io/rick-and-morty-react/). Исходный commit: **b70fef2810896b9764e5175dd239ae6b145df485**. В опубликованной странице наблюдался bundle **index-PFm8c2b1.js**; наличие этого файла само по себе не доказывает тождество bundle указанному commit.

Окружение: **macOS 27.0.1**, **встроенный браузер**. Версия браузера/движка интерфейсом не раскрыта. Это не запуск в отдельном Google Chrome. Основной CSS viewport: **1440 × 1000 px**; в TC-15 дополнительно проверены **320 × 1000** и **768 × 1000 px**.

Метод: **проверки интерфейса с помощью браузерного инструмента**, чтение DOM и взаимодействие с опубликованным приложением. Все описанные ниже результаты относятся к этому выполнению. Это не ручной прогон пользователя в Chrome, не набор Playwright-тестов и не результат существующих Vitest-тестов с mocks. Отдельной проверки в физических мобильных устройствах не было.

Основание проверок: пользовательские сценарии приложения и рабочие QA-ожидания, сформулированные для этого прогона. Для **TC-12 и TC-13** ожидания по фокусу и прокрутке являются предложенными UX-критериями; требуется согласование с владельцем продукта и triage. Статус Failed означает наблюдаемое расхождение с этими критериями. Полный аудит WCAG не проводился.

Все фактические результаты приведены по [журналу браузерных наблюдений](evidence/browser-observations.json) и приложенным снимкам. HTTP-статусы запросов приложения этим набором не подтверждаются. В частности, данные модального окна сверялись с карточкой и интерфейсом, без независимой проверки содержимого ответа backend: отдельная попытка такого запроса вернула 403.

Приоритеты ниже — предложенный порядок выполнения регрессии: P1 — основной пользовательский поток; P2 — дополнительная проверка удобства и устойчивости. Приоритет кейса не равен severity дефекта.

## TC-12

**Название:** Фокус после отправки поиска клавишей Enter

**Приоритет:** P2.  
**Предусловия:** каталог персонажей; клавиатурный фокус в поле «Поиск по имени»; CSS viewport 1440 × 1000 px.

**Шаги:**

1. Ввести Rick в поле поиска.
2. Отправить форму обычной клавишей Enter.
3. После обновления результатов проверить активный элемент.
4. Нажать Tab и проверить следующий активный элемент.
5. Повторить отправку клавишей Enter для Morty.

**Ожидаемый результат:** согласно предложенному UX-критерию фокус после отправки сохраняется в поле имени либо намеренно переводится к доступному заголовку/началу результатов. Если фокус остаётся в поле имени, следующий Tab переводит его на поле статуса. Ожидание требует подтверждения владельцем продукта.

**Фактический результат:** поиск выполнился. В двух повторах из двух после Enter активный элемент изменился с INPUT на BODY; поля содержали соответственно Rick и Morty, маршруты — #/characters?name=Rick и #/characters?name=Morty. После проверенного нажатия Tab фокус вернулся на INPUT с id character-name, вместо перехода к статусу.

**Статус:** Failed, воспроизводимость потери фокуса 2/2. Зарегистрирован [BUG-001](bugs/BUG-001.md); требуется UX-triage, это не вывод полного аудита доступности.

**Доказательства:** [перед Enter](evidence/BUG-001-before-enter.jpg), [после Enter](evidence/BUG-001-after-enter.jpg), [после Tab](evidence/BUG-001-after-tab.jpg); [журнал, записи TC-12-before-enter, TC-12-after-enter, TC-12-after-tab и TC-12-repeat](evidence/browser-observations.json).

## TC-13

**Название:** Переход из футера к персонажам

**Приоритет:** P2.  
**Предусловия:** открыт раздел эпизодов; CSS viewport 1440 × 1000 px.

**Шаги:**

1. Прокрутить раздел эпизодов к футеру.
2. Перейти к персонажам по ссылке/логотипу футера.
3. Проверить маршрут, сохранённую позицию прокрутки и положение заголовка нового раздела.
4. Вернуться к эпизодам и повторить переход из футера.

**Ожидаемый результат:** согласно предложенному UX-критерию переход к другому разделу показывает начало страницы либо заголовок нового каталога, чтобы пользователь видел контекст и элементы управления. Ожидание требует подтверждения владельцем продукта.

**Фактический результат:** переход к #/characters состоялся, но в двух повторах из двух scrollY сохранился равным 1109. Заголовок каталога находится выше видимой области: headingTop = -573.640625 px при высоте viewport 1000 px. ## TC-15

**Название:** Адаптивность на трёх размерах viewport

**Приоритет:** P1.  
**Предусловия:** приложение открыто во встроенном браузере; каталог персонажей загружен.

**Шаги:**

1. Установить CSS viewport 320 × 1000 px.
2. Проверить каталог, навигацию и поле поиска; открыть модалку и проверить её границы и кнопку закрытия.
3. Повторить проверки при 768 × 1000 px.
4. Повторить проверки при 1440 × 1000 px.
5. Зафиксировать ширину документа, сетку карточек и размеры диалога.

**Ожидаемый результат:** на каждом проверяемом размере каталог помещается по ширине, сетка адаптируется, поле поиска и навигация доступны; диалог находится внутри viewport и имеет доступную кнопку закрытия.

Сетка содержала 1, 2 и 4 колонки соответственно. Навигация, поле поиска и модалка помещались по ширине. Во всех трёх режимах верх и низ диалога находились внутри высоты 1000 px, высота кнопки закрытия составляла 44 px.
